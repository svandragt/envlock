# AGENTS.md

Guidance for coding agents working in this repository. `README.md` covers what envlock is for and how to use it.

## Layout

- `bin/envlock`: the whole tool, one bash script. `~/.local/bin/envlock` is a symlink to it.
- `skills/ticket-fleet/SKILL.md`: a Claude Code skill that starts a herdr worktree and session per ticket. `~/.claude/skills/ticket-fleet` is a symlink to it.
- `examples/vip.envpool`: an anonymised copy of a real pool config for VIP dev-env sites. The real file lives untracked in that project's main checkout.
- `examples/altis.envpool`: a pool config for Altis local-server sites. It was tested against a throwaway sandbox, not a real project.
- `tests/`: the test suite. `tests/run` runs every `t-*.sh` suite, `tests/lib.sh` holds their shared helpers and `tests/bin/herdr` is the stub herdr.

## How a lease works

- A lease belongs to a herdr agent, not to a command. The agent runs `envlock acquire [--wait SECONDS]` from its worktree when it is about to use an environment. `session_id` reads the caller's pane from `$HERDR_PANE_ID` and makes `acquire` exit 1 with a message when it is unset or `herdr` is not on `PATH`.
- `acquire` works in the foreground: it joins the queue, takes the lock, runs `envpool_configure` when the env lacks a needed attribute, runs `envpool_reset`, switches the environment (see the attach record below), and then starts the holder. The agent's command blocks until all of that is done.
- The lease is a `flock` on fd 9 of `$envdir/<env>.lock`. The holder is a process started with `setsid` that inherits fd 9. It runs `hold`, which starts `session_wait_idle` (`herdr agent wait <pane> --until idle --until done`) as a child with fd 9 closed, so only the holder keeps the lease. When the wait returns or fails, for any reason including a missing pane or server, the holder logs `released`, exits and the kernel releases the lock. `envlock release` sends the holder TERM, and the holder's trap kills its whole process group, so the wait ends with it and no process outlives the lease. The holder logs nothing on TERM, because `release` logs `released ... (release)` itself, so each lease end has exactly one `released` line. A `blocked` agent (a permission prompt) is neither idle nor done, so it keeps its lease.
- The holder's stdin is `/dev/null`, and its stdout and stderr go to `$lockdir/holder.log`. If it kept the caller's pipes, `name=$(envlock acquire)` would wait for it. Hook output goes to stderr for the same reason, so stdout carries only the environment name.
- Every hook runs through `hook`, which closes fds 7, 8 and 9 for that one call: the shrink or suspend candidate's lease lock, the pool lock and the lease. A process that a hook starts and leaves running, such as a daemon, then never inherits a lock that envlock still holds or has passed to the holder. Closing the fd when a block exits does not do this, because it does not reach a child that already started.
- After starting the holder, `acquire` closes its own fd 9, prints the environment name on stdout, and runs `headroom`. The lock now lives only in the holder, which is why `headroom`, `grow` and `shrink` all start with fd 9 closed.
- `$envdir/<env>.holder` reads `<worktree> (<branch>) pane <pane> pid <holder pid>`. `acquire` writes it without the pid first, so `find_lease` ignores a lease that is still being set up. `status` prints it as the holder, and affinity and `find_lease` match on the worktree prefix.
- `find_lease` finds this worktree's live lease: a holder file that names the worktree, whose pid has `/proc/<pid>/fd/9` pointing at that env's lock file. Holder files outlive their lease, so the `/proc` check is what makes a lease live. `acquire` (reuse), `env` and `release` all use it. On reuse, `acquire` prints the environment and exits 0 without queueing, resetting or attaching. With `--need`, a reused env that does not match gets `envpool_configure` in place first; without that hook `acquire` exits 1 and tells the caller to run `envlock release`. `--want` never touches a reused env. `release` kills the holder pid.
- A pane holds at most one lease. When `find_lease` finds none, `acquire` runs `release_pane_lease` before it queues: it ends every live lease whose holder file names this pane (`pane <id> pid`, plus the same `/proc` check) for another worktree. It kills the holder like `release` does, logs `released <env> <old label> pane <id> (moved to <label>)`, and waits up to 5 seconds for the env's lock to free, so the acquire that follows, even with `--wait 0`, can take that env. The old holder logs nothing on TERM, so the move leaves one `released` line. Leases of other panes are not touched.
- `$envdir` is `${XDG_STATE_HOME:-$HOME/.local/state}/envlock/envs`. It holds each env's `.lock`, `.holder`, `.attached` and `.suspended` files, so two repositories that list the same environment share one lock. `$lockdir` is `.../envlock/<hash of the git common dir>` and holds the rest: the queue, the grown-envs list, `last/`, `grow.lock` and the logs. All worktrees of one repository share a pool.
- `.envpool` is sourced from the worktree root, or else from the main checkout.
- `log` appends one line to `$lockdir/events.log`: `date +%FT%T`, the event, then the env, the branch (the worktree's directory name when there is no branch), `pane <id>` where known, and extras. The events are `queued` (with `need=` and `want=` pairs, and `urgent`), `leased` (with the holder pid), `reused`, `timeout`, `released`, `configure-failed`, `reset-failed`, `attach-failed`, `created`, `create-failed`, `grown`, `grow-failed`, `shrunk`, `destroy-failed`, `suspended` and `suspend-failed`; each failure carries `exit=<status>`. A line is one `>>` write, and a failing write never fails envlock. The holder's `released` reason is `idle or done` when the wait returned 0, because `herdr agent wait` does not say which, and `wait failed, exit=N` otherwise. `status` prints `events log: <path>` as its last line. `acquire` calls `trim_log` after each new lease: when the file is over 1 MiB it keeps the last 5000 lines through `tail` to a temp file and `mv`, without a lock, so a line that another process appends in between is lost.
- `acquire` prints `envlock: preparing <env>` when it takes the lock, and `envlock: using <env>` only after the holder runs, next to the name on stdout. A caller that stops reading after the first line (`2>&1 | head -1`) then never sees `using` for a lease that does not exist. `acquire` also ignores SIGPIPE (`trap '' PIPE`), so a closed pipe makes writes fail instead of killing it mid-attach. Its own messages end in `|| true`, and a hook that writes to the closed pipe fails like any failing hook: logged, no attach record, non-zero exit, lock released. Hooks inherit the ignored SIGPIPE.
- Waiters queue as files in `$lockdir/queue/`, named by nanosecond timestamp and pid. Only the oldest live entry may take an environment. `acquire --urgent` prefixes the name with `0`, which sorts before every timestamp, so urgent entries come first and stay in arrival order among themselves. An urgent waiter that arrives while a normal head is mid-attempt takes the head at the next poll.
- `ENVS` may be empty when `ENVPOOL_MAX` is above 0, `ENVPOOL_PREFIX` is set and `envpool_create` exists; otherwise envlock exits 1 with "sets no ENVS". An empty pool grows on the first `acquire --wait`, through the same `grow --capped` call that `acquire` makes when nothing is free.
- When `envpool_exists` and `envpool_create` are both defined, `acquire` checks an env from `ENVS` with `envpool_exists` after it takes the env's lease lock (`create_missing`). A missing env gets `envpool_create` under the pool lock (`flock -n`, so a held pool lock skips the env until the next poll), logged as `created` or `create-failed` with the exit status. The lease lock makes a second waiter skip that env while it is created, so it is created once. After a failed create the env stays unusable for the rest of that `acquire`, which then moves on to the next env or waits. Like growth, creating happens only with `--wait`, because it takes minutes. Grown envs are not checked. `status` shows a missing `ENVS` name as `not created`, without calling `envpool_describe`, and does not count it as free.
- `--need key=value` is the hard attribute and `--want key=value` the soft one. Both repeat and can be combined. `--need` decides which envs are eligible and drives `envpool_configure`. `--want` only ranks, so it never configures, never waits for a match and never fails on a mismatch.
- `try_order` ranks the pool for the queue head, and only the head tries. The rank is the sum of 4 for lacking a `--need` pair, 2 for lacking a `--want` pair and 1 when the holder file does not name this worktree, tried lowest first. So the order is: needs, wants and holder; needs and wants; needs and holder; needs; then the same four for envs that lack a need, in pool order within each. Without flags every env has every pair, so this reduces to holder first, then pool order. The holder rank lets a ticket get back the environment that already has its code. An env that `is_missing` (see create below) adds 8 to its rank, so it comes after every env that exists, with the same four ranks inside that group: a free existing env wins over a minutes-long create.
- An env has a pair when `envpool_describe` prints that exact `key=value` as one space-separated word. A missing or failing `envpool_describe` prints nothing, so the env has no pair. `--need` without the hook exits 1 before any queueing. `--want` without the hook is ignored, with one note on stderr. A flag value that is not `key=value` exits 2.
- Without `envpool_configure`, `try_order` leaves out the four ranks that lack a need. A waiter keeps its place in the queue until an env with the needs frees up or `--wait` runs out (exit 75). Growth is unaffected: a grown env may lack a need and is then left out, or configured when the hook exists.
- After taking an env's lock, `acquire` runs `envpool_describe` again, because the env may have changed since it was ranked. If the env lacks a need, `acquire` runs `envpool_configure` with every `--need` pair, and never a `--want` pair, before `envpool_reset` and `envpool_attach`. If that fails, `acquire` deletes the env's attach record, logs, and exits 1, which releases the lock because no holder exists yet.
- After taking an env's lock, `acquire` reloads the pool and checks that the env is still a member. If it is not, it closes the lock and tries the next env. This covers an env that a shrink removed after `acquire` listed the pool.
- The attach record is `$envdir/<env>.attached`, which holds the worktree path of the last successful switch. Before `envpool_attach` runs, `acquire` deletes the record. It writes the record only after `envpool_attach` returns 0, and a failing hook exits under `set -e` before that. `envpool_reset` and `envpool_attach` run as plain commands, because `hook ... || ...` would turn `set -e` off inside the hook. So the `EXIT` trap in `acquire` logs `reset-failed` or `attach-failed` with the exit status, using `$stage` to know which hook was running. `acquire` skips `envpool_attach` when the record names this worktree and either `envpool_healthy` is undefined or returns 0. `envpool_reset` still runs on every new lease, and not on reuse.
- After taking an env's lock on a new lease, `acquire` deletes the env's `.suspended` marker (see suspend below), before `envpool_configure`, `envpool_reset` and `envpool_attach`. A suspended env stays stopped until `envpool_attach`, so configure and reset can run against a stopped env.
- After an acquire leaves no environment free, a detached `envlock grow --capped` builds one in the background (`$lockdir/grow.log`). `grow.lock` is the pool lock: it stops two grows, or a grow and a shrink, running at once.
- Environments added by growth are listed in `$lockdir/envs`, not in `.envpool`.
- Every acquire writes `$lockdir/last/<sha1 of the worktree path>`: the worktree path on line 1, the env name on line 2. A worktree uses the env it leased most recently, so an env can have several users. An env is in use while any record whose worktree directory still exists names it.
- After an acquire, `headroom` either starts a grow (it returns 0) or does not. When it does not, a detached job starts in the same way, logging to `grow.log`. It runs `envlock shrink` when `envpool_destroy` is defined and `$lockdir/envs` is not empty, and then `envlock suspend` when `envpool_suspend` is defined. It starts nothing when neither applies.
- `envlock shrink` takes the pool lock with `flock -n` and exits if it is held. The candidates are the names in `$lockdir/envs` that are not in `ENVS`. For each one it takes the env's lease lock on fd 7 with `flock -n` and keeps it through `envpool_destroy`, so nobody can lease the env while it is removed. With that lock held it checks the rule again: no live record names the env, and another env, from `ENVS` or grown, has a lock that `flock -n` can take. It reloads the pool before each candidate, so the free count is taken again after every removal. It deletes the records of worktrees that no longer exist.
- A successful destroy removes the name from `$lockdir/envs`, still holding the env's lock, and deletes the env's `.holder`, `.attached` and `.suspended` files. It never deletes the `.lock` file: a lease that opened the file before the removal then locks the same inode, finds the name gone, and drops the lock. A failed destroy keeps the env registered and logs it.
- Shrink always leaves another env free at the moment of each removal, so it does not fight `headroom`, which only grows at 0 free. A lease can still take that env during a slow destroy. When it does, the lease's own grow finds the pool lock held, so `shrink` calls `headroom` again after a removal.
- A spare is a pool env, from `ENVS` or grown, that no live record names (`env_in_use`, the rule shrink uses) and whose lease lock `flock -n` can take. The seed env is not in the pool, so it is never a spare. A suspended grown env is still a shrink candidate, because shrink's rule ignores the marker.
- `envlock suspend` takes the pool lock with `flock -n` and exits if it is held. For each spare without a `$envdir/<env>.suspended` marker it takes the env's lease lock on fd 7 with `flock -n`, keeps it through `envpool_suspend`, and checks `env_in_use` with the lock held. It deletes the env's `.attached` record before the hook, so the next acquire always runs `envpool_attach`, which starts the env, even after a stop that failed halfway. On success it writes the marker. A failed suspend is logged and leaves no marker, so the next pass tries again.
- `envlock grow` runs the suspend pass after a successful grow when `envpool_suspend` is defined, so the new env, which no record names, is stopped. The grow that `acquire` runs while it waits does not, because that waiter takes the new env at once.

## Other agent hosts

- envlock depends on herdr only through `session_id` and `session_wait_idle`. To support another host, such as Orca, rewrite those two functions.
- `session_wait_idle` must only wait and must not `exec`: `hold` runs it as a child, logs after it returns, and ends it by killing the process group.
- A host needs two things: a way to identify the calling session, such as an environment variable set in its terminals, and a way to block until that session finishes its turn or exits.
- A host-free option for Claude Code is a `Stop` hook that runs `envlock release` at the end of each turn, with a holder that waits for the agent's process to exit instead of a herdr state. It works in any terminal, but only for Claude Code sessions.
- `skills/ticket-fleet` uses herdr to create worktrees and start sessions, so another host needs its own version of that skill.

## Platform contract

Every platform example in `examples/` gives agents the same behaviour, so a ticket works the same way whichever platform its project uses. `examples/vip.envpool` and `examples/altis.envpool` set the baseline, and a new platform, such as DDEV, must meet it. Each example:

- Gives each env its own stack and database, served at a hostname that contains the env name. Envs share only the platform's proxy.
- Attaches by pointing the env at the worktree's code and keeping its database, so a lease gets the database as the previous lease left it.
- Runs `viv install` in `envpool_attach` when the worktree has no `vendor` directory.
- Leaves the worktree's tracked files as they were, so git sees no change after an attach.
- Flushes the object cache across the network in `envpool_reset`, and tolerates a stopped env.
- Stops the env in `envpool_suspend`, succeeds when it is already stopped, and lets `envpool_attach` start it again.
- Reports a stopped env as existing in `envpool_exists`.
- Creates an env by cloning the seed's database, compares table counts, and destroys the half-built env when any step fails.
- Removes everything the env owns in `envpool_destroy`, and succeeds when it is already gone.
- Prints the site URL in `envpool_info`, and the wp-cli command when the platform's own command does not work from a leased worktree.

The platforms may differ only where the platform forces it:

| | VIP dev-env | Altis local-server |
|---|---|---|
| WordPress and PHP versions | The env owns them, so `envpool_describe` and `envpool_configure` exist and `--need` works | The worktree's `composer.json` sets them, so `--need` and `--want` do not apply |
| Attach | `vip dev-env update --app-code` repoints the env | The hook writes the env name into the worktree's `composer.json` for one `composer server start` and restores it |
| `envpool_healthy` | The php container runs | The php container mounts this worktree and the site returns 200 |
| Login | `envpool_info` prints an autologin URL | The seed's users, copied with its database |
| wp-cli | `vip dev-env exec` | `docker exec` into the env's php container |

## Writing .envpool hooks

- `envpool_create` runs inside an `if`, where `set -e` is off. Chain its steps with `&&` and return non-zero on failure, or envlock registers an environment that does not work.
- `envpool_destroy` runs inside an `if` as well. Chain its steps with `&&` and return non-zero on failure, or envlock forgets an env that still exists. It must also succeed when the env is already gone, or envlock can never forget an env that was removed by hand. The VIP example does both: it ignores a failing `vip dev-env destroy`, removes the files that containers wrote as another uid through a `busybox` container, and then succeeds only when the config directory and the containers are gone.
- `envpool_suspend` is optional and sees `ENVLOCK_ENV`. It stops the env to save memory. It runs inside an `if`, where `set -e` is off, so chain its steps with `&&` and return non-zero on failure. It should also succeed when the env is already stopped, or envlock logs a failure on every pass for an env that was stopped by hand. The VIP example runs `vip dev-env stop`.
- A suspended env stays stopped until its next acquire, which runs `envpool_configure` and `envpool_reset` before `envpool_attach`. So `envpool_attach` must start the env when it is stopped, and `envpool_reset` must tolerate a stopped env. The VIP reset ends in `|| true`, and its attach runs `vip dev-env start`.
- `envpool_exists` is optional and gets a name as `$1`. It returns 0 when an environment with that name exists outside the pool, such as one made by hand, and grow then tries the next number. It also decides whether `acquire` creates an `ENVS` name (see the queue above): the name is created only when this returns non-zero.
- `envpool_create` must leave a working database. The VIP example clones the seed environment's database, compares table counts, and destroys the new environment on any mismatch.
- `envpool_describe` is optional and sees `ENVLOCK_ENV`. It prints space-separated `key=value` pairs, such as `wp=7.1 php=8.4`. `status` appends its output to each env's line, and `--need` and `--want` match against it. envlock keeps no copy, because `envpool_configure` changes the answer. Output from a failing hook is dropped.
- `envpool_configure` is optional and sees `ENVLOCK_ENV` and `ENVLOCK_WORKTREE`. It gets every `--need` pair as an argument, matching or not, and must make the env match them. It never gets `--want` pairs. It runs inside an `if`, where `set -e` is off, so chain its steps with `&&` and return non-zero on failure. On an unknown key it should return non-zero.
- `envpool_attach` runs as a plain command, so `set -e` applies inside it and a failing step aborts `acquire` with no attach record. It must always do the full switch, because envlock decides when to skip it.
- `envpool_info` is optional and sees `ENVLOCK_ENV` and `ENVLOCK_WORKTREE`. `acquire` runs it after every successful acquire, new lease or reuse, once the env name is on stdout. Its stdout goes to stderr, so `name=$(envlock acquire)` gets only the name. A failing hook is ignored, because the lease is already taken. The VIP example prints the https autologin URL: over http a headless browser gets an http-only cookie, and its next https admin request bounces to the login page.
- The Altis example gives each env a local-server name, which is the env name. local-server reads the stack name only from `extra.altis.modules.local-server.name` in the composer.json of the directory it runs in, else from that directory's name, and its `start` refuses when `vendor/host` names another host. So `envpool_attach` writes the name into the worktree's `composer.json`, deletes `vendor/host`, runs `composer server start`, and restores both files byte for byte in a subshell `EXIT` trap, which also runs when the start fails under `set -e`. The name stays out of the worktree, so git sees no change and the next env started from it picks its own name. For the same reason `composer server cli` does not work from a leased worktree: with the name gone it looks for a stack named after the directory. Agents run wp-cli through `docker exec`, as `envpool_info` prints.
- `envpool_healthy` is optional and sees `ENVLOCK_ENV`. It returns 0 when the environment is up and serves its code. envlock asks it only when the attach record already names the worktree. Without it, the record alone decides.

## Testing

Run `tests/run` from any directory, about 40 seconds. It runs every `tests/t-*.sh` suite, prints each suite's `passed=N failed=M` line and exits non-zero if any suite fails, after listing the failing checks. Each suite tests `bin/envlock` in this checkout, never `~/.local/bin/envlock`. It keeps all its scratch state (git repos, `XDG_STATE_HOME`, pane files) in a `mktemp -d` directory that it removes on exit, so the real state under `~/.local/state/envlock` stays untouched.

`acquire` needs a `herdr` on `PATH` and `HERDR_PANE_ID` set. `tests/lib.sh` puts the stub `tests/bin/herdr` first on `PATH`. The stub's `agent wait <pane>` blocks until a file named after the pane appears in `$STUB_DIR`, or until `$STUB_DIR` is removed, and the stub refuses every other subcommand. A test creates the pane's file to simulate the agent going idle. Never call the real `herdr agent wait` or `herdr agent prompt` from a test.

New behaviour gets checks in a `t-*.sh` file: the matching suite, or a new `t-*.sh` file, which `tests/run` picks up. A suite calls `fresh <name>` for a scratch repo whose dummy `.envpool` hooks only log to `$TEST_LOG` (the `TEST_*` variables in `write_pool` in `tests/lib.sh` switch hooks on), runs `acq <dir> [args]` to acquire as a new pane, and records each observation with `check "description" command`. Run several `acq ... --wait N` calls in the background, each from its own worktree and pane, to exercise the queue. `tests/t-gaps.sh` puts a `sleep` in `$SCR/bin` that shortens the queue's 5-second poll to 0.3 seconds, and sets `TEST_DISK` so an env exists only after `envpool_create` runs. The suites reach the stub and envlock through symlinks in the scratch directory, so `pgrep` patterns on their command lines match only processes of that run. Anchor any new `pgrep` or `pkill` pattern and include `$SCR` in it, so a test never touches a real holder or `herdr wait`. Never test grow, create, shrink or destroy against a real project's environments.

To test the hooks for real, use a throwaway sandbox: a scratch git repo with its own devbox, its own seed environment and an untracked `.envpool` whose environments have a prefix no real project uses, such as `sbx`. Never create test tickets, branches or worktrees in a real project.

Check the scripts with `bash -n bin/envlock` and `shellcheck -x bin/envlock tests/*.sh tests/run tests/bin/herdr`; if shellcheck is missing, run it through devbox or `nix shell nixpkgs#shellcheck`.
